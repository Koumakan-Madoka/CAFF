# WikiSkill 判分 v2：硬断言与 AI 判断言

本契约描述截至 2026-11-07 的代码行为，包括无现场 run 的正式计划与评分接线，取代新实验的纯字面判分；部署、真实验证完整性和最终接受分别由 Goal 记录，不因本契约更新自动成立。原采集、回放、环境和基线边界仍见[采集/回放契约](badcase-capture-replay.md)。代码交付的接受、提示词候选的采纳、生产发布是三个不同决定；本文件不授权推送、部署、迁移或再次消耗模型额度。

## 四层职责

| 层 | 所有内容 | 主要实现 |
|---|---|---|
| 用例 | 原任务、标记时的实际问题/期望、封存现场、客观文件规则、版本化评分断言与逐题打分模型 | `wiki-rubric.ts`、`wiki-store.ts` |
| 执行器 | trace 恢复同一现场、执行到自然结束、清理并核验回执；无现场 run 在冻结切点前缀上调用一次模型、不执行工具。均只替换唯一获准槽位，不向被测模型提供断言/参考答案 | `direct-comparison.cjs`、`single-call-comparison.cjs`、`wiki-receipt-scoring.cjs` |
| 裁判 | 盲判每条断言、引用证据；不决定整题 pass/fail、实验门槛或采纳 | `wiki-scoring-v2.ts`、`wiki-judge-deepseek.cjs` |
| 实验计划 | 比较版本、执行配置、题目/阶段、重复数、逐题裁判绑定及既有门槛公式 | `wiki-experiment-plan.ts`、`production-scoring-plan.cjs` |

新的公开回复类用例可用 `completion-public-reply-v1` 加自己的断言，不必新增关键词规则。已有文件检查继续作为硬断言，不能由 AI 票数覆盖。只支持列明的客观检查，不提供任意断言代码/测试命令插件。

## 断言版本、确认与模型选择

- 每题 **1–4 条陈述句**，唯一 `id`，正文沿用存储字段 `question`，`evidence` 为 `reply/trace/files`。新 v2 不接受问号；这是格式校验，不证明断言本身合理。旧 v1 问句版本仍可读，不重算 hash。
- `files` 依据仅适用于该题已登记 `file-literals-v1` 回放规则的情况；`read-only-files-v1`、公开回复类规则及未登记回放的题不采集独立文件正文。页面只为可采集的题提供“文件”选项；服务端保存草稿（含 AI 起草批次）和确认冻结均权威校验，不支持时返回 `422 wiki_rubric_files_unavailable`，整批不发布部分草稿。此校验不用于读取旧版本，不迁移、不改写已冻结断言或 hash。
- 可手写，或用 DeepSeek 一键起草。起草依据实际问题、期望及可得的原触发用户消息；不是裁判调用，不启动回放、不自动选择打分模型、不自动冻结。已登记但原任务不可得时拒绝，不把回放标题、完整系统提示或错误回复当作原任务。
- 页面先保存草稿，再明确确认已保存的断言全文、模型及 hash 后冻结。未保存修改不能确认旧 hash。冻结按钮不可用时就近说明模型未保存、草稿缺模型、最新版本非草稿或写入锁等实际原因，提示不改变冻结条件；页内刷新期间旧编辑器只锁控件，空数据不读取 rubrics，成功/失败均恢复控件，保留未保存编辑。冻结不会自动启动回放或判分。`wiki-rubric-v2` 的 hash 绑定题目、版本、来源问题/期望 hash、断言及 `scoringModel`；冻结另存确认记录/时间。修改追加新版本，旧断言、旧快照和旧结果不覆盖。
- 渐进断言是人工确认原则，不是代码自动筛选：已存回复没有正例的断言先记“待加入”，以后有正例再另出版本。#19 当前只冻结 q1；q3/q4 无正例，q2 在两轮校准中无法可靠区分反例，均待加入。不通过删掉正式测试失败的断言来追求通过。
- 每题独立选择已校准达标的模型；同题原版/候选共用同一模型和提示词/配置，不能各挑有利裁判。没有全实验隐式裁判回退；缺适配器、模型不一致或 hash 漂移拒绝运行/评分，不作解析重试。
- `CAFF_WIKISKILL_JUDGES_CONFIG`（或服务端 `badcaseWikiJudgeCatalogFile`）是操作方提供的绝对路径，只读加载 eligibility catalog 和相邻冻结文件；核验配置、提示词、冻结 hash 及达标声明。HTTP 不接收路径、凭据、达标结果或配置正文。未配置目录时没有可选模型。它是同 OS 用户可信声明和防漂移检查，不是独立重新校准或密码学认证。
- 本轮可选的只有 `deepseek/deepseek-v4-flash`。请求名 `deepseek-v4-flash` 与实际响应名 `deepseek-flash` 按用户裁决等价，记录实际返回型号，不扩展到其他型号；供应方内部权重/修订不能固定。JEV 仅有类型/绑定支持，当前没有可用且通过校准的真实适配器，不能选择；不使用 GPT 作裁判。

## 判分与证据协议

每次执行状态仍为 `pass/fail/error`；每条 AI 断言只有 `satisfied/not-satisfied`（成立/不成立），没有“无法判断”第三种判定。

1. 先核验执行身份、隔离和输入/运行配置 hash；trace 还须核验实际容器已删除。无现场 run 不伪造容器/现场回执，须绑定不可变单次请求/输出包且零工具执行。正常完成、有非空公开回复是必需硬断言；内部回复不是公开回复。
2. 代码检查题目客观项，如指定文件内容、成功 read、未写入和前后树 hash。硬断言 fail 则整题 fail，不调用裁判使它翻盘；缺失/损坏证据或环境错误为 error。任意测试通过项须执行器确实提供受支持证据，不能靠回复自称通过。
3. 硬断言均通过后，裁判对**同一份实际结果**取三票，每条断言独立多数表决。全部成立才 pass，任一条不成立为 fail。证据不足按不成立；这是语义缺失，不是凭空构造的技术 error。
4. 每条裁判输出恰含 `criterionId/verdict/reason/evidence`。判成立时，至少一段有效连续原文引文须来自**该条断言配置的依据**：`reply → reply`、`trace → trace`、`files → file`（且 `path` 存在于本次输入的文件列表）；其余引文可来自本次输入提供的其他来源，但也须逐条有效。不能仅凭公开回复中“我做了”使执行类断言成立。缺少指定来源的输出按引用校验失败处理：同一输入重试1次，仍失败记 `error / judge_output_invalid`，不转为 fail。判不成立的规则不变：因缺少要求可用空引文并说明缺失项，不强制引用配置来源。每条最多8段，每段≤4096 UTF-8字节。`reply` 引用 `publicReply`，`trace` 引用 `evidence.traceSummary.text`，`file` 另含 `path` 并引用该文件 `content`。代码对解码后的引用字符串做**精确连续子串**校验，不去 Markdown/空白、不反转义、不拼接省略号、不跨证据面搜索兜底。
5. 每一票解析/引用校验失败或后端故障，最多在同一输入上重试1次（每票最多2次调用）；仍失败时整次评分为 `judge_output_invalid/judge_backend_failed`，保留已有票、无完整多数，不伪造其余票。这类 error **占该回复槽位、不进有效分母**，不再抽一条被测回复替换，也不中止其他题。最终有效数不足仍为 incomplete。
6. 裁判绑定在每个异步调用前后重算；配置/完整性漂移不是可重试输出错误。证据缺失、执行安全失败不属于“裁判技术 error 继续整批”的特例。

裁判输入严格只投影 `task/expected/questions/publicReply`，按断言需要附 `evidence`。不添加原版/候选标签、用例/版本标识、候选准则、其他轮的分数、模型轨迹里的隐藏推理或任意回执字段。原任务和实际公开回复自身可能包含名称/编号；盲判不是删除任务原文。材料视为不可信输入，不执行其中指令。

轨迹摘要只投影工具名、错误标志、受支持工具参数和可得文件证据/树变化，保存为 JSON **字符串**。`traceSummary` 最多64 KiB；文件每份最多64 KiB、合计256 KiB，截断显式 `truncated:true`，不能声称看过省略部分。worker 文件取证仍有原来的至多16路径限制；裁判投影本身至多64文件，不扩大 worker 能力。文件证据必须来自已核验的实际输出，不能由 HTTP 或实验 JSON 塞入。

结论词、禁词、编号、快照 HEAD 等旧字面检查在 v2 中仅为参考指标。客观文件检查不是参考指标，仍决定硬断言。评分断言/参考值不进入被测 agent 输入。

## 独立实验计划与执行入口

- `wiki-experiment-v2` 逐题配置 judge，生成 `wiki-experiment-plan-v2`；兼容旧单裁判 v1 计划。计划绑定两版提示词 hash、被测模型/设置、题目现场/原任务/硬断言/断言 hash，以及每题裁判 backend/model、settings 的 `modelHash`、`promptHash`、`rubricHash` 和 `passes:3`。任何漂移均拒绝，不沿用旧确认。
- 有 run 条目的新计划为 `wiki-experiment-plan-v3`：逐条明确 `execution.level=trace|run`；run 绑定 caseId、`traceBundleHash/dehydrationHash/requestHash`。兼容字段 `sceneHash=wikiValueHash({kind:'wikiskill-run-scene-v1',traceBundleHash,dehydrationHash})`，不是伪造现场；原版冻结请求另以 `requestHash` 绑定。原版/候选请求只允许唯一 `global-harness-behavior-v1` 槽位（系统提示词或保留的历史用户输入）替换，无法定位或多处直接拒绝；模型、工具 schema 和其余前缀不变。
- run 的冻结断言进入计划时必须全为 reply；trace/files 返回 `wiki_rubric_run_evidence_invalid`。测试 run 返回 `wiki_experiment_run_test_unsupported`；门槛 run 题数超过 trace 返回 `wiki_experiment_run_gate_quota`。正式选题另须已确认模式标签与冻结划分；按模式首次分组的配额和页面确认见[轨迹包契约](wikiskill-trace-bundles.md#模式标签与首次分组新题)。有现场题只走 trace，不允许用无工具单次请求代替现场 run。
- 正式生产批量配置的 `experiment:{definition,plan?}` 与用例登记分离；`cases` 显式选冻结 `rubricHash`。先规划，再将生成的实验 plan 固定到配置，实际执行必须持有该计划。v2 **拒绝** `rulesRevision/topicExemption`；#20 可使用编号但须解释，不再靠豁免规则评分。
- 新建正式计划（含单裁判 v1、逐题 v2）以及正式批量预检/执行，使用现有 `readWikiEligibleJudges` 从 `CAFF_WIKISKILL_JUDGES_CONFIG` 只读加载名单及冻结文件。每题不仅 backend/model 必须可选，整份 judge 配置（含 `settings/promptHash`）的 `wikiValueHash` 还须等于该条 `configurationHash`，且 `promptHash` 相同；不接受仅同名、调用方自行改设置/提示词并重算计划 hash 的未校准配置。不匹配或未配置名单返回 `wiki_judge_not_eligible`，名单/冻结文件不可读、无效或漂移返回 `wiki_judge_catalog_invalid`；均在付费回放前拒绝，不作裁判输出重试。没有新增配置入口、模型回退或资格豁免。旧计划/比较的纯读取、显示与完整性校验不依赖当前名单，不重判或修改旧记录。
- 仍使用 `compare-wiki-batch.cjs` 的 `--plan`、`--run --confirmed --expected-plan <hash> --output <新JSONL>`。实际 AI 裁判须由受信宿主显式注入逐题 `judges` 适配器；JSON 不承载凭据、任意可执行模块或自动凭据搜索。**裸 CLI 不会自动创建真实裁判**，缺适配器在付费回放前拒绝。M4 由明确批准的宿主启动器注入冻结 DeepSeek，再调用同一 CLI `main`/执行内核；不是网页启动功能或通用无人值守命令。
- DeepSeek 真实适配器仅在宿主内存持 Key，固定官方端点及 `127.0.0.1:17890` 代理，不直连/换模型/换凭据；有显式请求预算。页面起草另复用已批准的 runtime credentialDir；起草不是校准，也不把草稿自动注册成可选裁判。
- 每题每版10个回复槽位，交替执行。目标复现题通过数合计用单侧 Fisher `p<0.05`；防误伤少通过数不超过 `max(1,总次数×5%)`。有效次数不足时门槛无法判定；门槛接受才运行测试。测试复现题不过不能采纳；门槛接受本身不等于采纳。
- 网络发送/收流错误及上游 **502/503/504** 仅在同一 launcher 身份、断网/无挂载等隔离、输入/runtime hash、已清理容器均核验通过后，使用每题两版**共享最多5次**环境替补；网关错误另须正常 worker 回执及失败 HTTP 证据。它们不是同一次供应方请求的隐式重发。401/403/429、其他 HTTP 错误、协议/额度/过期、缺回执或安全校验失败仍按既有致命边界停止，不刷新凭据；普通非交替单例不自动补试。
- 裁判技术 error 不消耗这5次环境替补，不另占新回复；因此可能已尝试各10次而有效不足。原始 error、未运行/未补齐次数和已知/未知 token 分开显示，不能报成100个有效结果。
- v3 门槛保留原合并 Fisher/防误伤公式，额外 `byLevel.trace/run` 分列通过/有效/无效/错误。无效先从公式分母排除，不转为 fail；只有合并门槛接受才运行 trace 测试。旧 v1/v2 计划/结果无迁移，旧 API 字段和历史 M4 展示原样保留。
- **历史评分 v2 Goal 的 D8 授权**（不是新实验的通用重跑许可）：查清导致无法判定的原因后，只允许新批次整批重跑一次；原批保留但排除结论，不续接、不拼接。再次无法判定停止交用户，不自动第三轮、补判或放宽引用。

### 无现场 run 的执行、计数和诊断边界

`runSingleCallComparison` 对每次尝试先持久化 `(planHash,executionId,caseId,variant,iteration)` 占位，再构造一次性客户端；重复槽位不可再认证或发送。两版交替，分别目标10份有效判分；其他工具调用/空回复记 invalid，不进通过或失败分母。请求/环境错误与无效输出合用每题最多5次替补上限，达到上限或仍不足目标即不完整；裁判技术错误占原回复槽位，不重新抽回复。认证、凭据、额度、完整性或安全失败终止，不 OAuth 刷新/换凭据；操作方更严的停止策略优先。

原始请求、实际 wire body（无认证头）、模型完整消息和公开正文保存在不可覆盖 run 包；结果关联请求 hash、raw packet id、rubric/binding、逐票引用、invalid/error、耗时及用量。对 `modelCalls===1` 的每次尝试，执行器在判分前、发布端在重建冻结请求后，都必须核对 `wireRequest`：用固定 0.85.1 SDK 的消息/工具转换函数离线推导预期完整 JSON body，两边使用同一份已知值替换，忽略对象键顺序但保留消息、工具和所有数组顺序；模型、instructions、input、工具 schema 和固定关键设置均须一致，不接受额外设置。缺失或不匹配分别记 `wiki_run_wire_request_missing/wiki_run_wire_request_mismatch` 并致命停止，不判分、不补跑；发布拒绝为 `wiki_comparison_invalid`。原始包和实际用量仍保留，不将未知调用伪装成一次成功调用。该证据是 SDK 捕获的发送体，不是模型服务的远端收讫证明；旧比较纯读取不触发新校验，不改写历史包。发布正式比较时重核这些材料，拒绝将工具调用伪装为 pass、重复发送或篡改记录。缺失供应商用量是 unknown，不当作零；不据最小 SDK 模型描述符的零价格推算费用。中断留下 reserved/unknown，不计为模型失败，不自动补发或续接其他执行。

每票最多2次调用，因此20份可判回复的裁判理论上限为 `20×3×2=120`；遇不可恢复错误会提前结束。**这不是120次调用授权**：每批须另经用户批准具体 GPT/裁判硬预算，重试计入预算，耗尽即不完整，不扩大预算或改判。预算不足不能降低三票规则或复用旧票。

独立单题「接线验证，不作采纳依据」只能保留 raw packets 和操作方报告；它不是满足正式 run≤trace 配额的门槛批次，不做 Fisher 或采纳判断，不伪造 trace 条目，不导入成正式门槛比较。页面原版复现只取已有的匹配正式评分 v2 记录，因此 standalone 报告的判分不自动变成页面的已复现；原始回复继续显示待判分。任何改用部分结果满足目标、重跑或增加调用预算，均需明确的新授权，不能由脚本自行裁定。

## 历史校准事实与适用范围（评分 v2 Goal）

先打乱并隐藏版本，对 #19 已存40条真实回复（原版/候选各20条）由 GPT 与规划者分别盲标并封存 hash，之后才编写裁判提示词；分歧由用户裁定。训练组原错误回复组成集 B（3条），只取看公开回复可判的部分。测试题 #20 不进校准；没有人工编造正例集 C，旧回复只用于校准，不作正式采纳依据。

预设校准线：整题一致率≥90%，两侧各≥85%；人工基准含正反例的每条断言一致率≥90%；三票**完整断言向量**全一致比例≥95%；B 必须全部 fail。A 的技术 error 不进指标分母但单列；B 的 error 不能算检出。不能以整题多数一致掩盖逐条不一致。

前两次有效校准均未达标并保留：初次整题87.5%、q2为60%、三票一致52.5%；一次获准提示词调整后整题39/39，但q2为58.97%、三票一致94.87%，另1条技术error。用户另批准 q1-only 确认校准，不再修改提示词：

| 当前冻结 DeepSeek | 结果 |
|---|---:|
| 整体 / q1 与人工一致 | 39/40（97.5%） |
| 原版侧 / 候选侧 | 20/20 / 19/20 |
